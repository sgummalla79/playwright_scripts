Spike: Automating Phishing-Resistant MFA (PRMFA) for Playwright Testing

JWT Bearer flow + frontdoor.jsp session bridging, under Salesforce's phishing-resistant MFA enforcement for privileged users

Prepared2026-10-15
ScopeTechnical review of a proposed Playwright virtual-authenticator approach for unattended login as a privileged (Sysadmin-equivalent) Salesforce user, post-MFA-enforcement
StatusTechnically validated against the Playwright API and Salesforce documentation. See the Risk & Supportability section before using this in any pipeline.

1. TL;DR

The core idea in the spike is sound and the Playwright API calls are, with one ordering fix, real: Playwright ships a BrowserContext.credentials virtual WebAuthn authenticator (added in v1.61) that can register and replay a software passkey without any hardware, and Salesforce does not require hardware attestation for passkeys — a synced/virtual passkey is explicitly supported. So yes, this is technically possible.

Two things in the original spike need correcting before you build on it:

  1. Why the challenge appears at all is documented, not just empirically observed — see §3. It isn't a frontdoor.jsp quirk, it's by design: Salesforce never transfers a UI session's MFA assurance level onto an OAuth access token, so bridging that token back into a UI session (which is literally what frontdoor.jsp does) re-triggers the check.
  2. Salesforce's own documentation explicitly disclaims this exact workaround for privileged accounts — see §6. This changes the recommendation from "ship it" to "get this signed off before it goes into a pipeline against a Sysadmin-tier identity."

2. What PRMFA enforcement actually changed

"PRMFA" isn't a Salesforce product acronym — it's shorthand for phishing-resistant MFA, which Salesforce is enforcing for a defined tier of privileged users. A user counts as privileged if they have any of:

  • System Administrator profile
  • Author Apex permission
  • Customize Application permission
  • Modify All Data permission
  • View All Data permission

For direct UI logins, privileged users must complete MFA with a passkey (built-in authenticator or security key) — they can't fall back to Salesforce Authenticator or a TOTP app once enforcement is on. Non-privileged users still see passkey registration first, but can choose another method.

Confirmed in docs Salesforce does not require hardware attestation for passkeys. The platform explicitly supports "passkeys managed through a Password Manager or cloud keychain, provided it is FIDO2/WebAuthn-compliant" — i.e. software/synced passkeys are a first-class, supported credential type, not just a loophole. This is the real reason a Playwright virtual authenticator (also a software FIDO2 authenticator) is accepted.

3. Why JWT Bearer still hits AddPasskeyUi

This is the part the spike treated as an observed fact. Salesforce documents the mechanism directly, under Multi-Factor Authentication for API Access:

Salesforce documentation "Salesforce can prompt users to verify their identity twice with high-assurance MFA during an OAuth approval flow. The first challenge occurs in the UI session. The second challenge occurs when the client app bridges the access token into the UI. This second challenge happens because Salesforce doesn't transfer the high-assurance MFA session security level to the access token."

JWT Bearer is one of the OAuth flows Salesforce explicitly supports for high-assurance MFA session security (alongside web server, refresh token, and user-agent flows) — so it mints a valid access token with no interactive login. But that token carries no session-security-level pedigree. The moment you take that token's session ID and hand it to frontdoor.jsp — which exists specifically to bridge an existing session into a UI context — Salesforce evaluates session security for the UI session fresh, sees a privileged user with no qualifying MFA on this session, and redirects into passkey registration/assertion (/_ui/identity/webauthn/AddPasskeyUi). That's the mechanism; it isn't a bypass of API-level MFA (API logins themselves are MFA-exempt by default, and passkeys specifically can't be used to verify identity over the API at all) — it's the UI-bridging step re-asserting the UI-session requirement.

Worth validating in your org Public frontdoor.jsp documentation describes feeding it the SOAP API sessionId from a login() call, not an OAuth access token. Using an OAuth/JWT-Bearer access token as the sid parameter is a widely used pattern in practice, but it isn't the officially documented contract — confirm it continues to behave as expected in your target org/API version rather than assuming it's guaranteed.

4. Playwright's virtual WebAuthn authenticator — what's actually real

Verified against the current Playwright API docs (BrowserContext.credentials, added in v1.61):

Claim in the spikeStatusDetail
context.credentials.install() exists Confirmed Installs the virtual authenticator into the context, intercepting navigator.credentials.create()/.get() on all pages in that context.
Must call install() before navigating to the WebAuthn page Confirmed Docs state this as a hard requirement: "until install() is called, no interception is in place and the page sees the platform's native (or absent) WebAuthn behaviour."
context.credentials.create(rpId, options) signature Confirmed Accepts id, privateKey, publicKey, userHandle, signCount — all serializable, matching the spike's bootstrap/re-seed design.
Credential's private key can be serialized and re-seeded Confirmed This is intentional, per the W3C WebAuthn virtual-authenticator test API that Playwright implements (and that Chrome's DevTools Protocol WebAuthn domain exposes directly) — it's a testing primitive, not a Salesforce weakness. A real hardware or platform authenticator never exposes its private key this way.
Phase 1 then Phase 2 ordering in the spike's code Needs a tweak The Phase 2 sample calls credentials.create() then credentials.install() then page.goto(). That ordering works (seeding before install is allowed), but it's easy to get backwards. The one rule that matters: install() must happen before the goto() that triggers the WebAuthn ceremony — not necessarily before create().
Requires Playwright ≥ v1.61; Puppeteer needs raw CDP WebAuthn domain Confirmed No higher-level Puppeteer equivalent exists; you'd call WebAuthn.enable → addVirtualAuthenticator → addCredential via page.target().createCDPSession().

Corrected two-phase code

// Phase 1 — Bootstrap (one-time per org user)
await context.credentials.install();                      // must precede navigation
await page.goto(frontdoorUrl, { waitUntil: 'domcontentloaded' });
await page.waitForSelector('#savebtn');                    // Salesforce "Create Passkey" button
await page.click('#savebtn');                               // triggers navigator.credentials.create()

const [cred] = await context.credentials.get({});
// Persist: cred.id, cred.rpId, cred.privateKey, cred.publicKey, cred.userHandle
// Treat privateKey as a secret at the same tier as your JWT signing key —
// it is a complete, replayable MFA factor for this user, nothing weaker.

// Phase 2 — Unattended runs
const saved = loadFromSecretsStore();
await context.credentials.create(saved.rpId, {
  id: saved.id,
  privateKey: saved.privateKey,
  publicKey: saved.publicKey,
  userHandle: saved.userHandle,
});
await context.credentials.install();                       // before navigation, same as Phase 1
await page.goto(frontdoorUrl, { waitUntil: 'domcontentloaded' });
// navigator.credentials.get() is answered silently by the virtual authenticator

5. Things to validate before relying on this

  • rpId exactness. The spike's claim that rpId is the full org domain (e.g. yourorg.my.salesforce.com, not a salesforce.com suffix) is consistent with how WebAuthn relying-party IDs work, but isn't something Salesforce documents explicitly for this flow. Capture it exactly from the Phase 1 bootstrap run and don't hand-construct it.
  • One bootstrap click is unavoidable — correct. The virtual authenticator removes the need for a real biometric/security key, but something still has to drive the first navigator.credentials.create() call against a live challenge from Salesforce; there's no way to pre-generate a valid credential offline.
  • TOTP automation-user docs don't cover this tier — correct, and Salesforce says so explicitly (next section).

6. Risk & supportability — read before using this on a privileged account

This is the one correction that changes the recommendation Salesforce's own guidance on automation accounts states: "Phishing-resistant MFA doesn't work with automation or integration user accounts. Consider removing permissions if possible and completing MFA challenges programmatically with a third-party authenticator app. For use cases that require automation users to have privileged permissions, contact Salesforce Customer Support."

In other words: for the exact scenario this spike targets — a privileged, Sysadmin-equivalent automation identity — Salesforce's documented position is "talk to us," not "roll your own passkey emulation." A virtual WebAuthn authenticator satisfies the WebAuthn ceremony technically, but it is a self-engineered workaround for a control Salesforce built specifically to resist exactly this class of replayable, software-only credential for privileged accounts. That doesn't mean it won't work — it clearly can, mechanically — but it does mean:

  • Get this authorized in writing by the org's security owner (and, given the explicit "contact Salesforce Customer Support" language, consider actually looping in your Salesforce account team) before wiring it into any CI/CD pipeline against a Sysadmin-tier identity. This is squarely testing/QA automation, but it's also an unsupported path around a control that exists for a reason — treat the sign-off step as part of the implementation, not optional process overhead.
  • Scope down privilege first if you can. If the automation user doesn't actually need System Administrator / Author Apex / Customize Application / Modify All Data / View All Data, removing those permissions moves it out of the phishing-resistant tier entirely and back onto the officially supported TOTP path (mfa_automation_totp.htm).
  • Restrict to sandbox/non-production orgs for this pattern unless and until it's explicitly cleared for production use.
  • Store the serialized privateKey as a full MFA bypass credential, not just as test fixture data — anyone who obtains it can silently satisfy phishing-resistant MFA for that user, which is precisely the attack class passkeys exist to prevent. Same secrets-management tier as a signing key or a service account password, minimum.

7. Bottom line

QuestionAnswer
Is the Playwright virtual-authenticator mechanism real and does it work the way described? Yes — confirmed against the Playwright v1.61+ API and the W3C/CDP WebAuthn virtual-authenticator spec it's built on.
Does Salesforce accept a software/virtual passkey with no hardware attestation? Yes — Salesforce explicitly supports software/synced passkeys (password managers, cloud keychains); no attestation requirement blocks this.
Is the double-MFA-challenge behavior (JWT Bearer token survives, but frontdoor.jsp re-triggers passkey) documented, or a quirk? Documented behavior — session security level is never carried onto an access token by design.
Is this an officially sanctioned pattern for a Sysadmin-tier automation user? No — Salesforce's own docs say to contact Salesforce Customer Support for exactly this case. Proceed only with explicit sign-off.
